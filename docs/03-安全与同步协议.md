# 安全模型与同步协议

> 版本：v0.1（待评审）
> 本文档是 ReedShell 的安全与同步实现依据，改动需评审并升级协议版本号。

---

## 1. 威胁模型

### 1.1 资产

| 资产 | 敏感度 | 存放位置 |
|---|---|---|
| 服务器地址/端口/用户名 | 高 | 客户端密文、云端密文 |
| 登录密码、私钥、私钥口令 | 极高 | 客户端密文、云端密文 |
| 端口转发/跳板配置 | 中 | 客户端密文、云端密文 |
| 用户偏好 | 低 | 客户端密文、云端密文 |
| 主密钥 MK / KEK | 极高 | 仅客户端内存 / 系统钥匙串 |
| 账号密码 | 高 | 不存储；仅派生 auth_key，服务端存哈希 |
| 邮箱、套餐、设备信息 | 中 | 服务端明文 |
| 会话内容（终端 I/O） | 极高 | **不落盘、不上传** |

### 1.2 信任边界

```
[用户设备]  ──TLS──►  [服务端进程]  ──►  [MySQL / Redis / 备份]
   可信                 不可信              不可信
```

- 客户端信任：用户密码、设备 OS 钥匙串、安装包签名。
- 服务端**不信任**：任何上传内容、任何请求头、任何客户端计算的版本号。
- 服务端**不可信**：从用户视角，服务端可能被入侵、被管理员滥用、被执法调取；因此服务端不得具备解密能力。

### 1.3 在范围内

| 威胁 | 对策 |
|---|---|
| 服务端数据库泄露 | 全字段端到端加密；服务端只存密文与最小元数据 |
| 服务端管理员越权 | 管理员 API 与用户 API 隔离；管理员无解密代码路径；审计日志 |
| 中间人攻击 | TLS 1.3 + HSTS；SSH 主机密钥 TOFU 校验 |
| 重放/篡改同步包 | AEAD + AAD 绑定版本与身份；版本乐观锁 |
| 被盗设备（已锁屏） | 本地库密文 + 系统钥匙串 + 应用锁 |
| 恶意同步载荷 | 解密失败即丢弃并告警；大小/数量配额 |
| Web XSS/CSRF | CSP、HttpOnly Cookie、CSRF token |
| 支付回调伪造 | 易支付签名校验 + 金额比对 + 幂等 + 时间窗 |
| 暴力破解/撞库 | 限流、Argon2id、统一错误提示、异常登录通知 |

### 1.4 不在范围内（需明示）

- 已 root/jailbreak 或已植入键盘记录器的设备。
- 解锁状态下的物理访问。
- 构建流水线被完全攻破（仅靠代码签名与可复现构建部分缓解）。
- 流量分析（服务端可见记录数、大小、时间）。
- 拒绝服务（仅做基础限流，不做抗 DDoS 承诺）。
- 量子计算威胁。

### 1.5 已知残余风险（已接受）

本项目采用**密码包裹主密钥**的方案（决策 D8），不引入独立的 Secret Key。由此产生一个必须如实披露的残余风险：

| 风险 | 说明 | 缓解 |
|---|---|---|
| 数据库泄露后的离线字典攻击 | `wrapped_mk_by_pw` 可作为密码猜测的验证器；攻击者拿到库后可在本地反复尝试，不受服务端限流约束 | 强制密码强度（≥10 位且 zxcvbn ≥ 3，拒绝常见弱口令）；Argon2id 64 MiB / t=3；登录限流；异常登录通知 |
| 服务端内存中被捕获 | 登录瞬间服务端可见 `auth_key`（非密码、非 KEK），不足以解密 | 独立派生标签；服务端二次哈希；日志禁记 |
| 恶意服务端下发 Web JS | Web 登录使用加密密码；服务端被黑并篡改前端时，可捕获密码，再结合泄露的 `wrapped_mk` 解密 | **已接受（D9）**；CSP 禁止内联与第三方脚本、SRI + 构建哈希校验、无外部字体/CDN；Web 不提供改密与恢复码操作；引导高安全用户优先使用客户端 |
| 回滚攻击 | 服务端可返回旧版本密文；客户端靠版本号单调性拒绝 | 已实现版本单调校验；首次同步的新鲜度无法自证（见 §5.5） |
| 元数据泄露 | 记录数量、大小、更新时间、设备与 IP 可见 | 不存 `kind/name/parent`；IP 日志 7 天滚动；密文可选用 256B 桶填充 |

> 若未来需要把该风险降为零，可升级为协议 v2：引入 160 bit Secret Key，`KEK_pw = HKDF(root, salt=SecretKey)`，使服务端失去离线验证能力。届时不需重新加密历史数据，只需重新包裹 MK，但新设备加入需扫码/恢复密钥。

## 2. 密钥体系

```
                       用户记住的唯一秘密：密码
                                 │
                  Argon2id(password, kdf_salt, params)
                                 │
                              root(32B)  ── 仅存在于客户端内存
                    ┌────────────┴────────────┐
        HKDF(info="reedshell/auth/v1")   HKDF(info="reedshell/enc/v1")
                    │                         │
                auth_key(32B)               KEK(32B)
                    │                         │
         上传后服务端 Argon2id 存储      XChaCha20-Poly1305 解包
                                              │
                                         MK(32B, 随机)
                                        ┌─────┴──────┐
                                  包裹形式 1        包裹形式 2
                                wrap(KEK, MK)   wrap(recovery_key, MK)
                                  上传服务端        上传服务端
                                        │
                          HKDF(salt=item_id, info="reedshell/item-key/v1")
                                        │
                                   item_key(32B) ──► 加密单条记录
```

### 2.1 参数

| 项 | 值 |
|---|---|
| KDF | Argon2id，v=0x13 |
| 内存 | 桌面 64 MiB，移动 32 MiB（服务端下发的 `kdf_params` 有下限校验） |
| 迭代 | t=3，p=1 |
| `kdf_salt` | 16 字节随机，注册时生成，服务端保存（公开） |
| root | 32 字节 |
| auth_key | `HKDF-SHA256(root, salt=∅, info="reedshell/auth/v1")` |
| KEK | `HKDF-SHA256(root, salt=user_id, info="reedshell/enc/v1")` |
| MK | 32 字节 CSPRNG |
| item_key | `HKDF-SHA256(MK, salt=item_id_bytes, info="reedshell/item-key/v1")` |
| AEAD | XChaCha20-Poly1305，24 字节随机 nonce |
| 恢复码 | 160 bit 熵，Crockford Base32，32 字符，分 8 组 × 4 字符 + 2 位校验 |
| recovery_key | `HKDF-SHA256(SHA256(规范化后的恢复码), salt=user_id, info="reedshell/recovery/v1")` |
| 设备密钥 | Ed25519（设备签名）+ 32 字节随机 device_wrap_key（本地包裹 MK） |
| 授权签名 | Ed25519，公钥内置客户端 |

### 2.2 为什么服务端拿不到 MK

1. 服务端只收到 `auth_key`，`auth_key = HKDF(root, "auth")`，与 `KEK = HKDF(root, "enc")` 是单向函数的两个独立输出，无法互相推导。
2. 服务端存储的 `wrapped_mk_by_pw` 是用 KEK 加密的 MK，没有 KEK 无法解密。
3. Web 端同样只派生 `auth_key`（浏览器内 hash-wasm），服务端与浏览器之间不传输密码与 root。
4. 服务端代码**不依赖解密实现**；CI 强制检查 `reedshell-server` 的依赖树中不得出现 `chacha20poly1305`、`reedshell-crypto` 的解密 feature。

> 残余风险：登录时服务端可在内存中短暂看到 `auth_key`，但该值不足以推导 KEK/MK；服务端若主动作恶，只能做离线字典攻击 `auth_key → 密码`，其成本等于破解 Argon2id。登录限流可进一步抬高成本。

## 3. 账号生命周期

### 3.1 注册

**密码要求**：长度 ≥ 10，且通过强度检测（zxcvbn ≥ 3）；本地内置常见弱口令表，命中即拒绝。密码强度是当前密钥方案的最后一道防线。

```
1. 客户端本地已有 MK（Free 用户首次使用即生成并存入钥匙串）；若无则生成
2. 生成 kdf_salt(16B)，按 2.1 派生 root / auth_key / KEK / recovery_key
3. wrapped_mk_by_pw = AEAD(KEK, MK, aad="reedshell/mk/pw/v1"|user_id)
   wrapped_mk_by_rc = AEAD(recovery_key, MK, aad="reedshell/mk/rc/v1"|user_id)
4. POST /v1/auth/register
   { email, auth_key, kdf_salt, kdf_params, wrapped_mk_by_pw, wrapped_mk_by_rc }
5. 服务端存 Argon2id(auth_key)（再哈希一次，防止库泄露直接登录）
6. 返回恢复码（明文只展示一次，客户端不落盘；用户自行保存）
```

**升级路径**：Free → Pro 注册时直接使用现有本地 MK，无需重加密任何本地记录；注册完成后把本地全部记录标记为待推送。

### 3.2 登录（新设备）

```
GET  /v1/auth/params?email=...        → { kdf_salt, kdf_params, kdf_version }
本地派生 root → auth_key, KEK
POST /v1/auth/login { email, auth_key, device: {...}, device_pubkey, signature }
                                      → { access_token, refresh_token, wrapped_mk_by_pw, entitlement }
本地 unwrap MK
可选：用 device_wrap_key 包裹 MK 存入系统钥匙串（“记住此设备”）
```

- 错误提示统一为“邮箱或密码不正确”，不区分账号是否存在。
- 连续失败 5 次后该邮箱+IP 组合进入指数退避；失败 20 次/小时锁定 15 分钟。
- 新设备首次登录发送邮件通知。

### 3.3 设备绑定与令牌

- 每台设备生成 Ed25519 设备密钥，公钥在登录时注册；服务端 `devices.public_key` 唯一。
- Access Token：JWT（EdDSA），15 分钟，含 `sub / device_id / jti / exp`。
- Refresh Token：32 字节随机，服务端只存 SHA-256，30 天，**每次刷新轮换**。
- 刷新时必须提供设备签名：`sign(device_key, "refresh" | device_id | challenge)`；服务端验签。
- 刷新令牌复用检测：已轮换的旧令牌再次出现 → 判定泄露 → 吊销该设备全部令牌。
- 设备吊销后：Refresh 立即失效，Access 最多 15 分钟内失效；同步接口额外查 `devices.revoked_at`（每次请求校验，不等令牌过期）。

### 3.4 修改密码

```
1. 旧密码派生 KEK_old → 解包 MK（服务端不参与）
2. 新密码 + 新 kdf_salt 派生 root_new / auth_key_new / KEK_new
3. wrapped_mk_by_pw_new = AEAD(KEK_new, MK)
4. POST /v1/auth/password
   { auth_key_old（证明身份）, auth_key_new, kdf_salt_new, kdf_params_new, wrapped_mk_by_pw_new }
5. 服务端校验 auth_key_old → 更新哈希与包裹 → 吊销除当前设备外的 Refresh Token（可选）
6. 恢复码不变（仍包裹同一个 MK）；用户可主动重新生成
```

**关键点**：MK 不变，因此历史密文无需重加密，其他已解锁设备不受影响，只需下次用新密码解锁。

> Web 端**不提供**改密与恢复码重生成：这两个操作需要接触 KEK/MK，应只在已安装的客户端完成，减少浏览器侧暴露面（D9）。

### 3.5 忘记密码 / 恢复

| 场景 | 流程 |
|---|---|
| 记得密码 | 正常登录 |
| 忘记密码，有恢复码 | 输入恢复码 → 解包 MK → 设置新密码 → 重包裹 → 上传 |
| 忘记密码，无恢复码，但某设备仍已解锁 | 在该设备上修改密码（不需要旧密码，因为 MK 在内存/钥匙串） |
| 全部丢失 | **数据不可恢复**。可重置账号：删除云端密文、重新开始。UI 必须明确警告 |

恢复码界面要求：注册时强制展示 + 要求用户勾选“我已保存”；设置页可重新生成（旧恢复码立即失效）。

### 3.6 账号删除

- 用户确认后：30 天冷静期（可撤销）→ 硬删除 `vault_items`、`devices`、`wrapped_mk_*`、会话令牌；保留订单/发票的法定留存字段（脱敏）。
- 删除后恢复码与密码均无法恢复数据。

## 4. 记录加密格式

### 4.1 明文结构（仅客户端可见）

每条记录为一段 UTF-8 JSON（规范化：键按字典序、无多余空白）：

```json
{
  "schema": 1,
  "kind": "host",                 // host | ssh_key | forward | jump | snippet | pref | known_host
  "id": "01JABCDEF...",
  "parent_id": "01J...",
  "created_at": 1735689600,
  "hlc": { "wall": 1735689600123, "counter": 0, "device": "01JDEV..." },
  "data": { "...": "按 kind 定义的字段" }
}
```

- 层级（分组）信息在密文内，服务端不感知。
- `data` 字段随版本演进，使用 `schema` 兼容旧数据。

### 4.2 密文包络（服务端可见）

```json
{
  "item_id": "01JABCDEF...",
  "version": 7,
  "deleted": false,
  "nonce": "base64(24B)",
  "ciphertext": "base64",
  "size": 512
}
```

- 服务端只保存：`item_id`、`version`、`deleted`、`nonce`、`ciphertext`、`size`、`updated_at`。
- **不保存** `kind`、`parent_id`、名称、主机名、用户名、时间戳（客户端时间）。
- 删除（墓碑）时 `ciphertext` 为空、`nonce` 全零、`size=0`，仅保留 `deleted=1` 与版本号。

### 4.3 AEAD 绑定

```
AAD = b"reedshell/item/v1\0"
    || lp16(user_id)          // 2 字节大端长度 + UTF-8 字节
    || lp16(item_id)
    || u32be(version)

ciphertext = XChaCha20Poly1305::encrypt(item_key, nonce, plaintext, aad)
```

- 版本号进入 AAD：服务端篡改版本号会导致解密失败（客户端会校验并丢弃）。
- `item_key` 每记录独立：单条泄露不影响其他记录。

### 4.4 本地存储

- 本地 SQLite 存储与服务端完全相同的 `nonce/ciphertext/version`，打开时按需解密。
- 本地库密钥：
  - Free 用户：首次启动生成随机 32B `LocalMK`，存系统钥匙串；`item_key = HKDF(LocalMK, item_id, "reedshell/local-item/v1")`。
  - Pro 用户：直接用 MK（不再区分），迁移时在注册流程中把 `LocalMK` 作为 MK 上传包裹。
- 敏感字段不出现在 SQLite 的明文列、索引、WAL、临时文件、日志中。
- SQLite 设置：`journal_mode=WAL`、`secure_delete=ON`、`foreign_keys=ON`；DB 文件位于用户应用数据目录，权限 0600。
- 内存中的明文用 `zeroize` 在 drop 时擦除；解密结果不常驻超过一次操作。

## 5. 同步协议

### 5.1 状态

```
客户端：items(本地状态) + outbox(待推送) + cursor(已拉取到的服务端序号)
服务端：vault_items(每用户每记录一行) + sync_counters(每用户递增序号)
```

### 5.2 写入路径（客户端）

```
用户修改 → 本地事务：更新 items(密文, hlc, dirty=1) + 写 outbox
        → UI 立即生效（乐观）
        → 同步调度器防抖 2s 后触发 Push
```

### 5.3 Push

```
POST /v1/sync/push
{
  "device_id": "01JDEV...",
  "changes": [
    { "item_id": "...", "base_version": 6, "deleted": false,
      "nonce": "b64", "ciphertext": "b64" }
  ]
}
```

约束：单次 ≤ 100 条、总密文 ≤ 1 MiB、单条 ≤ 256 KiB。

服务端对每条记录（同一事务内）：

| 情况 | 处理 |
|---|---|
| 记录不存在且 `base_version=0` | 插入，`version=1`，分配新 `change_seq` |
| 记录存在且 `base_version=当前 version` | 更新，`version+1`，分配新 `change_seq` |
| 记录存在但版本不匹配 | 不写入，加入 `conflicts` 返回当前密文 |
| `base_version=0` 但记录已存在（含墓碑） | 冲突 |
| 用户配额超限（20,000 条 / 50 MiB） | 413 `quota_exceeded` |

响应：

```json
{
  "accepted": [ { "item_id": "...", "version": 7, "seq": 1234 } ],
  "conflicts": [ { "item_id": "...", "version": 9, "deleted": false,
                   "nonce": "b64", "ciphertext": "b64" } ],
  "server_time": 1735689600
}
```

**幂等性**：请求超时后客户端重试同一 `base_version`。若服务端已提交，会返回冲突且密文与本地待推送密文相同（逐字节比较 nonce+ciphertext）→ 客户端视为成功。

### 5.4 Pull

```
GET /v1/sync/changes?since=<seq>&limit=200
→ {
    "changes": [ { "item_id": "...", "seq": 1310, "version": 4, "deleted": false,
                   "nonce": "b64", "ciphertext": "b64" } ],
    "next_since": 1310,
    "has_more": true
  }
```

- 服务端返回 `change_seq > since` 的记录（每记录只返回其**最新**状态），按 `change_seq` 升序。
- `next_since` = 本页最大 `change_seq`；`has_more` 表示还有下一页。
- 客户端逐页拉取直到 `has_more=false`。
- `limit` 默认 200，最大 500。
- 若 `since` 小于服务端保留的最小序号（墓碑已清理），返回 `410 cursor_expired`，客户端执行全量快照。

### 5.5 全量快照

```
GET /v1/sync/snapshot?cursor=<opaque>&limit=500
→ { "items": [...], "next_cursor": "...", "has_more": true }
```

- 快照按 `item_id` 排序分页，避免长事务；期间发生的变更通过后续 Pull 补齐（快照游标带起始 `seq`）。
- 仅在首次登录、`cursor_expired`、用户手动“重新同步”时使用。

### 5.6 冲突判定（客户端）

每条记录携带 HLC，冲突在客户端解决：

```
新版本胜出条件（字典序比较）：
  (wall, counter, device_id) 更大者胜
```

流程：

1. Push 返回冲突 → 解密服务端当前版本。
2. 比较 HLC：
   - 本机更新 → 以服务端版本为新 `base_version` 重新推送本地内容。
   - 服务端更新 → 应用服务端版本，把本地版本写入 `conflicts` 表并在 UI 提示。
3. 最多 3 轮；仍冲突则双方都进入 `conflicts`，交给用户选择“保留本机 / 保留云端 / 另存为副本”。

**已知限制**：记录级 LWW，同一连接的两个字段在不同设备同时修改时，旧的整条会被覆盖。缓解：偏好设置按 key 拆成独立记录；连接字段冲突会进入冲突箱，不静默丢失。

### 5.7 HLC

```
本地事件：
  wall = max(物理毫秒, last.wall)
  counter = if wall == last.wall { last.counter + 1 } else { 0 }

收到远程 HLC：
  wall = max(物理毫秒, last.wall, remote.wall)
  counter = 视 wall 来源按上述规则合并
```

- 设备时钟偏差不影响最终一致性，只影响“谁更新”的判断；极端偏差下用户可从冲突箱恢复。

### 5.8 删除与墓碑

- 删除 = 写入 `deleted=1` 的新版本，分配新 `change_seq`。
- 墓碑保留 **90 天**，之后由清理任务物理删除。
- 离线超过 90 天的设备会收到 `410`，走全量快照（本地未推送的修改仍保留，以冲突方式合并）。

### 5.9 调度

| 触发 | 行为 |
|---|---|
| 本地写入后 2s（防抖） | Push |
| 应用前台每 60s | Pull |
| 窗口重新获得焦点 | Pull |
| 手动点击同步 | Push + Pull |
| 网络恢复 | Push + Pull |
| 登录/设备注册完成 | 全量快照 + Pull |

- 失败退避：1s → 2s → 4s → ... → 60s，带抖动；连续失败 10 次暂停并提示。
- 同步为单飞（single-flight），同一时刻只有一个同步任务。

### 5.10 配额与限流

| 项 | 限制 |
|---|---|
| 记录数/用户 | 20,000 |
| 密文总量/用户 | 50 MiB |
| 单条密文 | 256 KiB |
| Push 频率 | 60 次/分钟/设备 |
| Pull 频率 | 120 次/分钟/设备 |
| 并发设备 | Pro 10 台 |

超限返回 `413 quota_exceeded` / `429 rate_limited`，客户端指数退避并提示。

## 9. 授权与计费

- 套餐与功能开关由服务端配置，客户端不硬编码价格。
- 登录/同步响应携带 `entitlement`：

```json
{ "plan": "pro", "features": ["sync"], "device_limit": 10,
  "exp": 1736294400, "iat": 1735689600, "nonce": "01J..." }
```

- Ed25519 签名，客户端内置公钥离线校验；篡改即失效。
- 有效期 7 天；离线宽限 14 天；超过宽限则本地功能仍可用，同步暂停并提示上线。
- 到期/退款：服务端把 `plan` 置为 `free`，下次刷新授权后客户端进入“只读同步”3 天，然后停止同步，本地数据保留。

### 9.1 易支付 V1 接入

**下单**

1. Web 选择套餐 → `POST /v1/billing/checkout { plan: "pro_month" | "pro_year" }`。
2. 服务端创建 `orders` 行（`status=pending`），生成 `out_trade_no`（ULID），金额取自后台配置（月 600 分 / 年 6000 分）。
3. 按易支付 V1 规范拼装参数：`pid`、`out_trade_no`、`notify_url`、`return_url`、`name`、`money`、`sitename`、`sign`、`sign_type`。
   - **不传 `type` 字段**，由聚合收银台让用户选择支付方式。
   - `money` 为元，保留两位小数（如 `6.00`、`60.00`）。
4. 签名：参数按键名 ASCII 升序，剔除 `sign`、`sign_type` 与空值，拼接为 `k=v&k=v...`，末尾直接追加商户密钥，MD5 取小写（若服务商提供 RSA2 则优先使用）。
5. 服务端返回 `{ pay_url }`；浏览器跳转到该地址（`GET` 或自动提交表单，以服务商文档为准）。

**异步通知（唯一发货依据）**

1. 接收 `GET/POST /v1/billing/notify`，原始参数保存到 `orders.raw`。
2. 重新计算签名并比对；校验 `pid`、`trade_status=TRADE_SUCCESS`、`money` 与订单金额完全一致。
3. 按 `out_trade_no` 加行锁查询订单：
   - 已支付 → 直接返回 `success`（幂等）。
   - 未支付 → 事务内更新 `status=paid`、写入 `provider_order_id=trade_no`、延长订阅、写审计。
4. 响应体必须为纯文本 `success`（无 JSON、无多余空白）；否则服务商会重试。

**同步跳转**

- `/v1/billing/return` 仅用于展示结果页，验签后重定向到 `/billing/result?order=...`；**不得**据此发货。

**补偿与对账**

- 定时任务每 5 分钟查询 `pending` 超过 5 分钟的订单（易支付查询接口），防止通知丢失。
- 每日对账：拉取服务商账单与本地 `orders` 比对，差异进入管理员待处理列表。

**退款**

- 管理员在后台标记退款；若服务商支持退款接口则调用，失败转人工处理并记录审计。
- 退款成功后立即将订阅置为 `canceled`，按剩余天数决定是否降级。

**风险**

- 聚合支付服务商的可用性、结算与合规风险由运营方承担；需在服务条款中明确支付由第三方提供。
- 订单状态的权威来源是「异步通知 + 主动查询」双通道，不以同步跳转为准。

## 11. 安全加固清单

### 服务端

- [ ] 仅 HTTPS，HSTS（含子域），TLS 1.2+（优先 1.3）
- [ ] 请求体上限 2 MiB；同步包 1 MiB
- [ ] 注册/改密强制密码强度（≥10 位、zxcvbn ≥ 3），拒绝常见弱口令
- [ ] 登录/注册/找回：Redis 令牌桶，按 IP + 邮箱双维度
- [ ] 统一认证错误文案；响应时间做恒定化处理
- [ ] JWT 使用 EdDSA，校验 `alg`、`exp`、`jti`、`device_id`
- [ ] Refresh 轮换 + 复用检测 + 设备签名
- [ ] 管理员强制 TOTP；可选 IP 白名单；所有写操作进入 `audit_logs`
- [ ] Web 会话 Cookie：`HttpOnly; Secure; SameSite=Lax; __Host-` 前缀
- [ ] CSRF double-submit；CSP `default-src 'self'`；`X-Content-Type-Options: nosniff`
- [ ] CORS 仅允许配置的前端源
- [ ] 易支付异步通知：验签（MD5/RSA 以服务商为准）、`pid` 匹配、金额与订单一致、`out_trade_no` 幂等、时间窗校验
- [ ] 易支付商户密钥仅存服务端环境变量，不下发客户端、不写日志
- [ ] SQL 全部参数化（sqlx）；无字符串拼接
- [ ] 无 SSRF 面：服务端不请求用户提供的 URL
- [ ] 数据库最小权限账号；Redis 不暴露公网
- [ ] 密钥/证书走环境变量或 secret 文件，不入库不入仓
- [ ] 依赖审计：`cargo-deny`、`cargo-audit`、`npm audit` 在 CI 中阻断
- [ ] CI 检查：`reedshell-server` 依赖树不含解密实现

### 客户端

- [ ] 本地库密文存储；密钥在 OS 钥匙串
- [ ] 主密码/应用锁；空闲自动锁定（默认 15 分钟）
- [ ] `zeroize` 擦除 MK、KEK、密码、私钥
- [ ] 日志脱敏；崩溃报告不含敏感字段
- [ ] 主机密钥 TOFU；变更阻断
- [ ] 剪贴板敏感内容自动清除（默认 30 秒）
- [ ] 多行粘贴确认；粘贴内容不回显到日志
- [ ] 更新包签名校验（Ed25519 manifest + SHA-256）
- [ ] 禁止在 WebView 中渲染远程内容（本项目无 WebView）

### Web

- [ ] hash-wasm 计算 Argon2id（与客户端参数一致）
- [ ] 不在 `localStorage`/`sessionStorage` 存储任何密钥或令牌
- [ ] 页面离开时清理内存中的派生密钥
- [ ] 第三方脚本最小化（支付仅外跳易支付收银台，不加载其脚本）

## 12. 灾难场景

| 场景 | 结果 | 恢复 |
|---|---|---|
| 服务端数据库泄露 | 攻击者仅得密文与元数据 | 无数据泄露；建议提醒用户轮换服务器密码（防御性） |
| 服务端被完全控制 | 可篡改/删除密文、拒绝服务 | 客户端检测 AEAD 失败并告警；本地数据完整 |
| 丢失一台设备 | 该设备保留已同步的本地密文 | Web/其他设备吊销该设备；远程无法擦除本地数据（需明示） |
| 丢失全部设备但有恢复码 | 数据可恢复 | 新设备用恢复码解包 MK → 重设密码 |
| 恢复码与密码全丢，但有设备在线 | 可在该设备改密码 | 打开客户端 → 设置 → 修改密码（无需旧密码） |
| 恢复码、密码全丢且无设备 | 数据永久丢失 | 仅能重置账号 |
| 用户误删连接 | 墓碑同步到所有设备 | 冲突箱/回收站保留 30 天（本地） |
| 时钟严重错乱 | 冲突判定可能偏向错误一方 | 冲突箱人工恢复 |

## 13. 测试要求

### 13.1 密码学测试向量

实现时必须固化以下测试（固定输入 → 固定输出）：

| 向量 | 内容 |
|---|---|
| KDF | 固定密码/盐/参数 → root、auth_key、KEK |
| AEAD | 固定 MK/item_id/version/明文 → item_key、nonce、ciphertext |
| AAD 篡改 | 修改 version/user_id/item_id 任一字节 → 解密失败 |
| 包裹 | 固定 KEK/MK → wrapped_mk 字节 |
| 恢复码 | 固定恢复码 → recovery_key；校验位错误必须拒绝 |
| 授权 JWT | 固定 claims → 签名；篡改任一字段 → 校验失败 |

### 13.2 同步一致性测试

- 属性测试（proptest）：随机并发写 + 随机断线，最终所有设备收敛到同一状态。
- 幂等测试：同一 Push 重放 10 次，结果一致。
- 冲突测试：两设备同时改同一记录，必有一方进入冲突箱且无静默丢失。
- 墓碑测试：删除 → 新设备全量同步后不可见；90 天后清理 → 旧游标返回 410。
- 配额测试：超限返回 413 且不写入。
- 零知识测试：服务端集成测试扫描所有响应，断言不含明文主机名/用户名。

### 13.3 安全测试

- 认证绕过、越权（A 用户访问 B 的 item）、令牌重放、设备吊销后访问。
- Web：XSS、CSRF、CSP 违规、开放重定向。
- 限流有效性（脚本压测）。
- 依赖漏洞扫描作为 CI 门禁。
